# 규칙

이 저장소에서 글 쓰고 커밋하는 방식을 정리했습니다. 처음에 한 번 읽고, 헷갈릴 때 다시 보면
됩니다.

## 문체

### 어디에 어떤 말투를 쓰나

`CLAUDE.md`만 단정형입니다. 매 세션 에이전트가 제일 먼저 읽는 규칙집이라 "만들지 않는다",
"묻지 않는다"처럼 짧게 끊어야 규칙으로 읽힙니다. 존댓말로 쓰면 어미가 길어지면서 지시가
흐려집니다.

나머지는 존댓말입니다. `docs/` 아래 문서, README, PR 설명, 이슈, 리뷰 코멘트가 여기
해당합니다. `docs/DECISIONS.md`는 한 줄짜리 기록이라 예외로 명사형으로 끝냅니다.

커밋 메시지는 둘 중 어느 쪽도 아닙니다. 아래 커밋 항목에서 따로 다룹니다.

### 번역투 걷어내기

제일 많이 걸리는 부분입니다. 영어로 생각한 문장에 한국어 단어만 끼워 넣으면 문법은 맞는데
읽다가 한 번 걸립니다.

| 이렇게 쓰지 마세요 | 이렇게 쓰세요 |
| --- | --- |
| 달라진 지점을 짚어준다 | 무엇이 달라졌는지 짚어준다 |
| 회사 코드와 다른 지점이라 | 회사 코드와 다르니 |
| 이게 이 규칙이 있는 유일한 이유다 | 이 규칙은 그래서 있다 |
| 캐시를 통해 응답을 가져온다 | 캐시에서 응답을 가져온다 |
| 성능에 대한 개선이 필요하다 | 성능을 손봐야 한다 |
| 데이터의 정합성을 확보한다 | 데이터가 어긋나지 않게 한다 |
| 효율적인 방식으로 처리한다 | 한 번에 처리한다 |

몇 가지만 기억하면 됩니다.

- `~을 통해`, `~에 대한`, `~에 있어서`는 빼세요. 조사 하나면 끝납니다.
- `지점`, `부분`, `측면`을 두루뭉술하게 쓰지 마세요. 진짜 위치를 가리킬 때만 씁니다.
- `~적(的)`은 대체할 말이 없을 때만. 효율적, 안정적, 직관적은 보통 빼도 뜻이 삽니다.
- 명사를 쌓지 말고 풀어서 쓰세요. "지표 추이 표시 기능 구현"보다 "지표가 어떻게
  움직였는지 보여준다"가 읽힙니다.
- "이 문서는 ~을 설명합니다"로 시작하지 마세요. 그냥 설명을 시작하면 됩니다.
- `또한`, `그러나`, `따라서`를 문장마다 달지 마세요. 순서만 맞으면 없어도 읽힙니다.
- 한 문장에 한 가지만. 쉼표로 세 번 이어 붙였으면 끊을 자리입니다.

### 영어를 그대로 두는 경우

억지로 옮기면 더 안 읽힙니다. 이런 건 그냥 둡니다.

- 코드에 그대로 나오는 이름: `Repository`, `UiState`, convention plugin, `stateIn`
- 이미 영어로 굳은 말: 레이트 리밋, 마이그레이션, 캐시, 토큰, 디버깅
- 고유명사와 API 이름: Ktor, Koin, RSO, VAL-MATCH-V1

반대로 화면에 뜨는 글자와 게임 용어는 한글이 기본입니다. `CLAUDE.md`의 용어표를 따릅니다.
한글로 적는 곳이면 문서든 주석이든 같은 표를 봐야 합니다. 문서에서는 척후대라고 하고
주석에서는 이니시에이터라고 하면 그때부터 두 단어가 따로 굴러다닙니다.

코드 식별자는 예외로 영어를 씁니다(`Queue.SPIKE_RUSH`). 한글 식별자는 스택 트레이스와
도구에서 다루기 어렵습니다. 식별자는 화면에 그대로 띄우지 않고 문자열 리소스를 거칩니다.

### 길이

한 문장 40자쯤, 한 문단 네 줄 안쪽이면 적당합니다. 줄은 96자에서 끊습니다. 표와 코드
블록은 넘겨도 됩니다.

## 커밋

### 형식

```
<type>(<scope>): <제목>

<본문>

<트레일러>
```

타입과 스코프는 영어 소문자로 고정합니다. 도구가 읽어가는 값이라 흔들리면 안 됩니다.
제목과 본문은 한글로 씁니다. 이 앱은 도메인 용어가 죄다 한글입니다. 퍼블을 first blood로,
타격대를 duelist로 적기 시작하면 용어표를 지킬 이유가 없어집니다.

```
feat(report): 주간 리포트 고정 지표 4종 카드 추가

전투점수, K/D, 피해량, 헤드샷을 항상 같은 자리에 둔다. 동적 지표는 다음 커밋에서.

Refs: CLAUDE.md#지표-규칙
```

### 타입

| 타입 | 언제 |
| --- | --- |
| `feat` | 유저가 쓸 수 있는 게 늘었을 때 |
| `fix` | 의도와 다르게 돌던 걸 고쳤을 때 |
| `ui` | 화면에 보이는 것만 바뀌었을 때. 색, 간격, 문구, 애니메이션 |
| `refactor` | 동작은 그대로 두고 구조만 바꿨을 때 |
| `perf` | 속도나 메모리를 손봤을 때 |
| `test` | 테스트만 건드렸을 때 |
| `docs` | 문서만 건드렸을 때 |
| `build` | Gradle, 의존성, convention plugin, CI |
| `style` | 포매팅만. 로직은 한 줄도 안 바뀜 |
| `chore` | 위 어디에도 안 들어가는 잡일 |

`ui`는 표준 Conventional Commits에 없는데 따로 뒀습니다. 이 앱은 화면 규칙이 곧 제품
규칙이라 "버튼 간격 4dp 조정"을 `feat`이나 `fix`에 넣으면 이력이 탁해집니다. `style`은
ktlint나 Spotless가 만든 변경에만 씁니다.

### 스코프

모듈 이름을 그대로 씁니다.

`onboarding` · `report` · `match` · `friend` · `settings` · `model` · `network` · `data` ·
`designsystem` · `app` · `build` · `docs`

여러 모듈에 걸치면 스코프를 뺍니다. 세 개 넘게 걸쳤으면 대개 커밋을 쪼갤 때입니다.

### 제목

- 한글 40자 안쪽. 한글은 글자당 정보가 많아서 영어 50자 기준을 그대로 쓰면 깁니다.
- 마침표 안 찍습니다.
- 명사형으로 끝냅니다. "추가", "수정", "제거". "추가한다"나 "추가했습니다"는 안 씁니다.
- 무엇을 했는지만. 왜 했는지는 본문에서 씁니다.

### 본문

왜 이렇게 했는지를 씁니다. 무엇을 바꿨는지는 diff가 이미 보여줍니다.

판단이 갈릴 수 있었던 자리, 다른 선택지를 버린 이유, 나중에 되돌릴 때 알아야 할 것.
이 정도면 충분합니다. 뻔한 커밋이면 본문 없이 제목만으로 끝내도 됩니다.

줄은 72자에서 끊습니다.

### 트레일러

| 트레일러 | 언제 |
| --- | --- |
| `Decision:` | `docs/DECISIONS.md`에 항목을 추가한 커밋에. 날짜와 한 줄 요약 |
| `Refs:` | 근거가 되는 문서 위치. `CLAUDE.md#지표-규칙` 같은 형태 |
| `BREAKING CHANGE:` | 저장된 데이터를 못 읽게 되는 변경. 제목의 타입 뒤에 `!`도 함께 |
| `Co-Authored-By:` | 에이전트가 같이 작업한 커밋 |

`Decision:`이 이 저장소에서 제일 중요한 트레일러입니다. `.githooks/pre-commit`이 지금은
경고만 띄우고 지나가는데, 그 경고를 커밋 이력에 남기는 장치입니다. 나중에 "이 규칙 왜
이렇게 됐지" 싶을 때 `git log --grep='^Decision:'` 하나로 찾습니다.

```
feat(report)!: 동적 지표 기준선을 표준편차 1.5배에서 1.2배로

8주 표본으로 돌려보니 1.5배에서는 후보가 3개를 못 채우는 주가 절반이었다.
기본 지표로 떨어지면 리포트가 매주 똑같아 보인다.

기존에 저장된 주간 리포트는 새 기준으로 다시 계산해야 한다.

BREAKING CHANGE: WeeklyReport 스키마 변경. 마이그레이션 필요
Decision: 2026-09-19 · 동적 지표 기준선 1.2배
Refs: CLAUDE.md#지표-규칙
```

### 쪼개는 단위

커밋 하나에 한 가지만 담습니다. 리뷰하는 사람이 "이거 왜 바꿨어요?"를 한 번만 물어도 되는
크기가 적당합니다.

딱 하나 예외가 있습니다. 지켜야 할 선, 지표 규칙, 역할군, 용어, 색 토큰, 화면 구조가
바뀌면 문서와 코드를 **같은 커밋에** 담습니다. 따로 내면 그 사이에 문서와 코드가 어긋난
커밋이 남고, 하필 거기서 체크아웃한 다음 세션이 옛 규칙을 읽습니다.

## 브랜치

```
<type>/<영문-슬러그>
```

`feat/report-fixed-metrics`, `fix/match-list-duplicate`, `build/koin-4-upgrade`.

타입은 커밋과 같은 값을 씁니다. 슬러그는 영어 소문자에 하이픈입니다. 한글 브랜치명은 일부
도구에서 깨집니다.

## 문서

### 어느 문서가 무엇을 담나

| 문서 | 담는 것 | 안 담는 것 |
| --- | --- | --- |
| `CLAUDE.md` | 코드 쓸 때마다 필요한 규칙 | 배경 설명, 회의록, 지난 경위 |
| `docs/DECISIONS.md` | 기획과 달라진 결정. 날짜·무엇·왜 | 안 바뀐 결정, 긴 논의 |
| `docs/CONVENTIONS.md` | 글과 커밋 규칙 | 코드 스타일 세부. ktlint가 할 일 |
| `docs/FIRST-TASK.md` | 첫 세션 작업 순서 | 그 뒤의 계획 |

`CLAUDE.md`가 길어지면 규칙 사이에 배경 설명이 섞인 겁니다. 배경은 `DECISIONS.md`로 옮기고
결론만 남깁니다.

### 코드와 문서가 어긋났을 때

코드부터 고치지 않습니다. 어느 쪽이 맞는지 먼저 정합니다. 문서가 맞으면 코드를 고치고,
코드가 맞으면 문서를 고칩니다. 어느 쪽이든 어긋난 채로 커밋하지 않습니다.

판단이 안 서면 `DECISIONS.md`에 "미정"으로 한 줄 남기고 넘어갑니다. 아무 말 없이 두는
것보다 낫습니다.

## 테스트

테스트는 두 곳에 나눠 씁니다.

| 종류 | 위치 | 도는 곳 |
| --- | --- | --- |
| 로직 (지표 계산, 색 대비 등) | `commonTest` | 안드로이드 JVM과 iOS 둘 다 |
| Compose UI | `iosTest` | iOS 시뮬레이터만 |

UI 테스트를 `commonTest`에 두면 안드로이드 JVM에서 전부 터집니다. JVM에는 화면을 띄울
환경이 없습니다. iOS는 네이티브 테스트 호스트가 있어서 돕니다. 안드로이드에서도 UI
테스트를 돌리려면 Robolectric을 붙여야 하는데, `commonTest`에는 `@RunWith`를 달 수 없어
아직 안 했습니다.

도구는 `kotlin.test` + Turbine(Flow) + Compose UI Test입니다. 컨벤션 플러그인이 다
걸어주니 모듈에서 따로 적을 게 없습니다.

ViewModel 테스트는 `commonTest`에 둡니다. `stateIn(WhileSubscribed(...))`으로 만든 상태는
누군가 구독해야 흐르기 시작합니다. 구독자 없이 `uiState.value`를 읽으면 계속 초기값입니다.
그리고 구독자를 `runTest` 기본 디스패처에 띄우면 아직 안 돌아서 역시 초기값이 나옵니다.
바로 도는 디스패처에 띄웁니다.

```kotlin
backgroundScope.launch(UnconfinedTestDispatcher(testScheduler)) { viewModel.uiState.collect() }
```

이름은 백틱으로 감싼 한글 문장입니다. 무엇을 검증하는지가 리포트에 그대로 보입니다.

```kotlin
@Test
fun `시작 버튼을 누르면 onStart가 한 번 불린다`() = runComposeUiTest {
```

무엇을 테스트할지가 더 중요합니다. 이 프로젝트에서 값어치가 있는 건 세 종류입니다.

- **지표 계산.** KAST, 클러치 판정, 액트 경계, 표준편차 기준선. 숫자가 틀리면 제품이
  거짓말을 하는데 눈으로는 안 잡힙니다.
- **지켜야 할 선.** 비공식 고지가 화면에 있는지, RSO 전에 전적을 안 부르는지. 어기면
  키가 회수되는 것들은 사람이 기억하는 대신 테스트가 지키게 합니다.
- **디자인 토큰의 제약.** 색 대비처럼 눈으로 통과시켜 버리기 쉬운 것.

반대로 Compose 레이아웃이 픽셀 단위로 맞는지는 테스트로 좇지 않습니다. 그건 프리뷰가
할 일입니다.

### 돌리는 법

로직은 JVM에서 돌립니다. 몇 초면 끝나니 코드를 고칠 때마다 돌려도 됩니다.

```bash
./gradlew :shared:core:model:testAndroidHostTest
```

UI는 시뮬레이터에서 돌립니다. 처음 한 번은 시뮬레이터를 띄우느라 몇 분 걸리고, 그 뒤로는
10초 안팎입니다.

```bash
./gradlew :shared:feature:onboarding:iosSimulatorArm64Test
```

### 테스트가 진짜 잡는지 보기

테스트가 통과한다고 테스트가 맞다는 뜻은 아닙니다. 규칙을 하나 새로 넣었으면 그 규칙을
일부러 지워 보고 테스트가 실패하는지 확인합니다. 안 깨지면 그 규칙을 지키는 테스트가 없는
겁니다.

지표 계산을 처음 짤 때 이렇게 확인했더니 트레이드 판정의 "우리 팀이 잡았는지" 조건을 아무
테스트도 지키고 있지 않았습니다. 그 조건을 빼도 전부 통과했습니다.

## 프리뷰

화면을 만들면 프리뷰를 같이 답니다. 최소 세 가지를 봅니다.

- 다크와 라이트
- 작은 기기 (320×568). 헤드라인과 버튼이 서로 밀지 않는지
- `fontScale = 1.5f`. 글자를 키운 사용자에게 줄이 넘치지 않는지

`@Preview`는 `androidx.compose.ui.tooling.preview.Preview`를 씁니다.
`org.jetbrains.compose.ui.tooling.preview` 쪽은 CMP 1.12에서 deprecated됐고 크기 인자도
못 받습니다.

테마와 배경은 `OvalitThemePreview`로 깝니다. 안 깔면 다크 토큰이 흰 캔버스 위에 떠서
실제와 다르게 보입니다.

색 토큰과 글자 위계는 `core/designsystem`의 `DesignSystemGallery`에 모여 있습니다.
토큰을 고쳤으면 거기부터 열어 봅니다.

## 화면 문구

Kotlin 상수로 두지 않습니다. 모듈별 `src/commonMain/composeResources/values/strings.xml`에
넣고 `stringResource`로 읽습니다. 로케일을 늘릴 때 `values-en`을 옆에 두면 끝나야 합니다.

문구를 추가하거나 지웠는데 `Unresolved reference '...'`나
`Unresolved reference '_collectCommonMainString0Resources'`가 나오면 생성된 접근자가 낡은
겁니다. CMP의 리소스 생성기와 AGP의 KMP 라이브러리 플러그인 사이에 갱신이 안 맞물리는
구간이 있습니다. `clean`으로는 안 잡히니 생성 디렉터리를 직접 지웁니다.

```bash
rm -rf shared/*/*/build/generated/compose
```

`\n`으로 줄을 바꾸지 않습니다. 기기 폭과 언어가 달라지면 그 자리에서 깨집니다. 줄바꿈은
타이포그래피가 맡습니다. `LineBreak.Heading`을 깔아두어 어절 경계에서 끊기고 마지막 한
단어만 남지 않습니다.

## 주석

웬만하면 달지 않습니다. 설명을 붙이고 싶어지면 대개 이름이 덜 다듬어진 상태입니다. 이름을
먼저 손보고, 그러고도 남는 것만 적습니다.

주석이 필요한 건 코드 밖에서 온 이유뿐입니다.

- 바깥 사정 때문에 이렇게 생긴 것. Riot API의 특이한 동작, AGP 제약, 플랫폼 버전 조건
- `CLAUDE.md`의 규칙을 코드에서 지키는 자리. 근거가 없으면 다음 사람이 "이거 왜 이러지"
  하고 고쳐버립니다
- 지우면 안 되는 것. 비공식 고지처럼 빼면 키가 날아가는 것

```kotlin
// economy.weapon은 라운드 시작 로드아웃이라 주워 쓴 총이 안 잡힌다.
val weaponId = kill.finishingDamage.damageItem
```

반대로 이런 건 다 지웁니다.

- 이름을 그대로 풀어 쓴 것. `/** 화면 좌우 여백의 기본값. */ val lg = 16.dp`
- 타입이 이미 말하는 것. `@param modifier 모디파이어`
- 코드를 한 줄씩 옮겨 적은 것. `// 리스트를 순회한다`
- 뻔한 값에 붙인 설명. 간격 상수, 색 이름, 데이터 클래스 필드
- 감상이나 취향. "한 화면에 둘이 있으면 둘 다 안 눌립니다" 같은 것

마지막 항목이 제일 걸러내기 어렵습니다. 그럴듯하게 읽히는데 정작 이 코드를 만지는 사람이
뭘 해야 하는지는 안 알려줍니다. 쓰기 전에 한 번 물어보세요. 이걸 모르면 뭐가 깨지나?
답이 안 나오면 주석이 아니라 디자인 문서에 들어갈 이야기입니다.

KDoc은 공개 API 중에 쓰는 쪽이 오해할 만한 것에만 답니다. 부르면 안 되는 자리가 있거나,
인자에 범위 제약이 있거나, 이름만 보고는 뭐가 돌아올지 짐작이 안 될 때입니다. 시그니처가
스스로 설명하면 KDoc도 군더더기입니다.

문체는 문서와 같습니다. 존댓말이고, 번역투는 걷어냅니다.
